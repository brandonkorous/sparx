# Tenant Seed Inventory & the Three-Layer Seeding Model

**Version:** 1.1
**Author:** Brandon Korous
**Last Updated:** 2026-06-17

## 0. What this is

An inventory of **everything a tenant would otherwise have to create by hand** to run a real
content/commerce business on sparx — grouped by module — plus the model for _how_ each thing gets
seeded so a fresh tenant lands on a working site instead of a pile of empty modules.

The driving question: when someone onboards, a working business needs emails, pipelines, content
types, shipping/tax config, automations, and much more. Which of those are **platform defaults**
(true for every tenant), which are **template content** (industry-specific), and which are **runtime**
(generated by usage and never seeded)? And when a module is toggled off and back on, what happens to
the tenant's data?

This is industry-agnostic: a CMS-only publisher, a CRM-only team, a wholesale distributor, and a DTC
shop are all first-class. "Tenant" throughout; "store"/"merchant" only where real selling is meant.

## 1. The three seed layers

Seeding happens at three distinct moments, for three distinct reasons. Conflating them (e.g. "seed
everything when the tenant is created") breaks the moment a tenant enables a module _later_ — it would
never get that module's defaults.

| Layer                      | Fires on                                                            | Scope                  | What it seeds                                                                                                                                                                            | Status                                            |
| -------------------------- | ------------------------------------------------------------------- | ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| **L1 · Provisioning**      | `tenant.created`                                                    | Tenant + primary site  | Primary `Property`, `<slug>.sparx.zone` `Domain`, `SiteConfig`, brand shell, legal pages + footer placements, default consent                                                            | ✅ live (provisioning + `legal-seed-worker`)      |
| **L2 · Module activation** | `module.activated(<slug>)`                                          | Per module, per tenant | Every **template-agnostic default** that module needs to not feel broken — default emails, system automations, CRM pipeline/segments, invoicing workflows/line-types, and the gaps below | ⚠️ partial (4 of 11 modules wired)                |
| **L3 · Blueprint install** | Template chosen at onboarding (or the fallback "Default" blueprint) | Per site               | All **industry-specific content** — brand/theme, pages, navigation, catalog, content entries, custom content types, example records                                                      | ✅ live but **narrow** (manifest covers a subset) |

**The base-blueprint question, resolved.** An early idea was "one base blueprint with everything built
in, auto-installed on tenant create." We are **not** doing that, for two reasons:

1. The template-agnostic defaults belong in **L2 (module activation)**, not a blueprint — otherwise a
   tenant who turns Commerce on next week never gets the commerce defaults. The codebase already does
   this correctly for CRM/email/automation/invoicing; the work is to **extend the same pattern** to the
   remaining modules (§5).
2. Blueprint **content** is the industry flavor — a bakery's products and a law firm's pages are not a
   "default," they're the template's whole point. So there is no meaningful "base blueprint with
   everything," only a generic **"Default / Blank Business" blueprint** that is the _fallback when no
   industry template is chosen_ (§5.C), with the L1/L2 defaults seeding underneath it regardless.

## 2. Seed-class taxonomy

Every entity in the inventory (§4) is tagged one of three ways:

- 🟢 **Platform default** — template-agnostic; every tenant on that module needs it. Seeds at **L2**
  (or L1 for cross-module foundations). Never carried by a blueprint.
- 🔵 **Blueprint content** — industry-specific; varies per template. Seeds at **L3**. The "Default"
  blueprint carries a generic version so no-template tenants still look finished.
- ⚪ **Runtime** — generated by usage. **Never seeded** (orders, carts, inventory movements, sessions,
  webhook deliveries, analytics, activities, deliveries). A _demo_ seed may fabricate examples for a
  showcase tenant, but that is dev-only, not onboarding.

## 3. Module lifecycle contract — the off → on rules (binding)

This answers "if a tenant disables a module, what happens to their data, and does re-enabling
overwrite it?" The pattern is already established and consistent across the live L2 consumers; every
**new** L2 seeder MUST follow it.

- **R1 — Deactivation never deletes.** Disabling a module leaves its rows in place, dormant: the module
  gate returns 404, workers idle, no _new_ rows are written (CLAUDE.md "stores no rows" = no new
  writes while off, **not** deletion). The CRM and invoicing consumers say it in code: _"On
  `module.deactivated` we keep the rows around — disabling is reversible and tenants would be upset to
  lose their edited pipeline on a brief disable."_ So the answer to "what do we do with their data" is:
  **keep it, dormant.**

- **R2 — Re-activation is find-or-create, never overwrite.** A seeder only creates what is **missing**
  (looked up by natural key — slug/key), so a tenant's _edited_ pipeline, emails, or workflows survive
  re-activation untouched. CRM bootstraps are "slug-keyed lookups → safe no-op"; email provisioning
  "creates only the missing keys." **No L2 seeder upserts over a tenant-owned row.** (Answer to "do we
  overwrite": **no.**)

- **R3 — Platform-managed content is the deliberate exception, and it still never touches tenant work.**
  System automations (`origin = 'system'`) re-sync to their canonical platform definition by key on
  reconcile — because they are platform-owned managed content, not tenant-authored. Tenants customize
  them by **cloning to a `user`-origin copy**, which is never touched. So even the one "overwrite" path
  only ever rewrites platform-owned rows, never a tenant's edits.

- **R4 — Sharp edge: find-or-create _resurrects deleted defaults._** Because L2 looks up by key and
  re-creates what's missing, a tenant who **deletes** a seeded default and then re-activates (or is hit
  by the self-healing reconcile cron) gets it back. This is **intentional today** — the same
  find-or-create powers the reconcile/backfill that seeds tenants who predate a seeder. The tradeoff:
  "seed every time it's missing" can't tell "never seeded" from "seeded then deliberately removed."
  Where deletion is a legitimate tenant choice (e.g. they run one custom pipeline and delete the
  default), use a **provisioning marker** — a per-(tenant, module) `seededAt` so the seed fires
  **exactly once** — instead of bare find-or-create. Decide this per entity (§6 D1).

**Net contract:** off = data kept dormant; on again = missing defaults refilled, tenant edits
preserved. No destructive deactivation, no clobbering re-activation.

## 5. What to build (punch-list)

Three workstreams, each independently shippable (deploy-early).

### 5.A — New L2 module-activation seeders (the biggest UX win)

Each is a `bootstrapXxx(ctx)` wired to `module.activated(<slug>)` on the platform bus, **find-or-create
by natural key**, **kept on deactivate** (R1–R3), with a daily reconcile/backfill (mirror the
automation + email reconcile pattern). Priority order = "what makes a freshly-enabled module feel
broken":

1. **Commerce** — ✅ `CommerceSiteSettings` (currency/locale/checkout + default warehouse link), one
   fallback `ShippingZone` + "Standard" profile + flat `ShippingRate`, and an **inactive** home
   `TaxZone` (no rates — the explicit "$0 until nexus / via provider" default) all seed on
   `module.activated(commerce)` (#74 + tax follow-up). _Return-policy + review-moderation have no
   config table — moderation is per-record at the service layer, so there is nothing to seed._
2. **Inventory** — ✅ one default operating `Warehouse` (`MAIN`) so stock has a home.
3. **Chat** — ✅ a starter `ChatQuickReply` bank (7 entries); widget greeting/hours live in chat settings.
4. **B2B** — ✅ a default `PurchaseApprovalRule`, seeded **disabled** — approval surface wired but inert.
5. **Saved-view presets** (platform-wide, not CRM-only) — ✅ `bootstrapSavedViewPresets` seeds a
   tenant-wide starter set of named list filters — the operational queues people live in (unfulfilled
   orders, overdue invoices, abandoned carts, pending reviews, credit-hold accounts) — for every
   preset-bearing module (commerce, crm, b2b, invoicing, cms). The earlier "deferred — no consumer"
   note is resolved: the platform `SavedView` API + the shared ListToolbar **"Views"** control shipped
   (#76), so these are live rows, not dead ones. Seeded **shared** (tenant-wide) and **never
   `isDefault`** — a default auto-applies on open, so a seeded preset must be an opt-in click, not a
   surprise filter — find-or-create by `(target, name)`, and **bundle-aware** (invoicing presets seed
   for Commerce/B2B tenants whose `invoicing` flag is never written). Catalog +
   seeder: `services/api-rest/src/lib/saved-view-presets.ts`.

Seeders 1–5 are wired through `services/api-rest/src/lib/module-provisioning.ts` (the in-process
`module.activated` consumer + 6h reconcile, sibling of `email-provisioning.ts`). Reference
implementations they copy: **CRM** (`packages/crm/src/consumers/module-activation.ts`), **Email**
(`services/api-rest/src/lib/email-provisioning.ts`), **Automation**
(`packages/automation-actions/src/seeds/`), **Invoicing** (same CRM consumer file).

### 5.B — Blueprint manifest extensions (L3 industry content)

Today the manifest carries `brand, theme, assets, contentTypes, content, commerce{categories,
collections, products}, components, layout, pages, emails`. Extend the schema + installer (one new
top-level section + one installer step each, in dependency order) to express the 🔵 gaps:

- CMS: `taxonomies[]` (+ terms), `authors[]`, explicit `navigation[]`.
- Commerce: `priceLists[]`, `discounts[]`, `bundles[]`, `configurators[]`, `fitment{}`,
  `shippingOverrides[]` / `taxOverrides[]` for industries that need specifics.
- CRM/B2B (optional demo): `crm{ pipelines?, exampleContacts?, exampleDeals? }`, `b2b{ tiers?,
accounts? }` — example records flagged demo, not default.

### 5.C — The "Default / Blank Business" blueprint (L3 fallback)

A real, installable blueprint that is the **fallback when the user picks no industry template**: a
generic-but-complete site (home/about/contact, starter nav, neutral theme, one example product + one
post, an empty-but-present pipeline) so a no-template tenant still lands on something finished. Not
auto-installed on tenant-create — selected (or defaulted) at onboarding, with L1/L2 underneath it.

## 6. Open decisions

- **D1 — Exactly-once vs self-healing per entity (R4).** Bare find-or-create resurrects a deliberately
  deleted default; a `seededAt` provisioning marker makes it exactly-once. Recommendation: keep
  self-healing for platform-managed/structural seeds (pipelines, emails, automations, line-types); add
  a marker only where deleting the default is a legitimate, sticky tenant choice. Decide per new seeder
  in 5.A.
- **D2 — Tax default stance.** Seed a real default `TaxZone`/`TaxRate`, or default to "tax handled by a
  connected provider (TaxJar/Avalara)" and seed nothing? Affects how broken checkout feels pre-provider.
- **D3 — Demo example records.** Do non-demo tenants get _any_ example CRM/B2B records (easier to learn
  the UI), or strictly empty-but-structured? Onboarding-friction tradeoff ([15](15-merchant-onboarding-prd.md)).
- **D4 — Default operating warehouse naming.** Auto-named ("Main") vs prompt during onboarding.
