# Start Here

## Objective

Ship Piggles as a credible alternative presentation of the same class of business capability currently embodied by Sparx, and allow both brands to compete for traction without intentionally handicapping Piggles.

## Strategic bet

Sparx is powerful, modular, technical, and the name is crowded. Piggles is memorable, approachable, less crowded, and can present the same serious capability without demanding that the customer think in software categories.

The test should be fair:

- do not cripple Piggles;
- do not force Piggles to inherit Sparx terminology;
- do not force Piggles to inherit Sparx pricing;
- do not rebuild every backend capability independently.

## First milestones

### 1. Product shell

Piggles visual identity, terminology, navigation, MDI chrome, workspace persistence, product-level flags.

### 2. Get Piggles

Signup, sign in, verification, password reset, business creation, onboarding, app selection, provisioning, billing handoff, secure transition into My Piggles.

### 3. My Piggles

Piggles Home, intent launcher, core MDI apps, progressive disclosure, workspace persistence, favorites/recent/workspaces.

### 4. Meet Piggles

Homepage, pricing, features/use cases, trust/security, docs/help, SEO, conversion paths.

### 5. Commercialization

$49 flat plan, capacity metering, simple expansion, billing events, entitlement enforcement.

## UI implementation rule

Piggles uses **SilicaUI**. Do not create a competing local component/theme vocabulary. Use the semantic SilicaUI theme mapping documented in `docs/brand/SILICAUI_THEME.md`.

## Core rule

A user should never be blocked from an ordinary business capability merely because they did not buy the corresponding "module". Enabling an app changes the workspace, not the subscription price.
